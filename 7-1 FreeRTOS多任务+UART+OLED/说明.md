# FreeRTOS 多任务＋UART DMA＋软件 SPI OLED

本例程在 STM32F103C8T6 上运行官方 FreeRTOS V11.2.0，外设仍使用 **STM32 标准外设库 SPL V3.5.0**。沿用独立 Keil 工程、中文注释和 Start / Library / User / System / Hardware 目录；额外的 FreeRTOS 目录存放未修改的官方内核及许可证。

## 环境与接线

STM32F103C8T6，8MHz 外部晶振，72MHz 主频，64KiB Flash / 20KiB SRAM。Keil ARM Compiler 5，和前六个工程相同。打开本目录 `Project.uvprojx`，F7 编译，通过 SWD 下载 `Objects/Project.hex`，BOOT0=0 后复位。

本例程按前面面包板方案，**用 PB14/PB15 普通 GPIO 模拟 SPI**。不同于前六个工程的 PB3/PB5 硬件 SPI；切换固件时也要切换这两根线。

| OLED 丝印 | STM32 | 说明 |
|---|---|---|
| GND | GND | 与开发板、USB-TTL 共地 |
| VCC | 3.3V | 从开发板 3.3V 给兼容模块供电 |
| D0 / CLK | PB14 | 普通推挽输出，软件时钟 |
| D1 / DIN | PB15 | 普通推挽输出，软件数据 |
| RES | PB12 | 低有效复位 |
| DC | PB1 | 低命令、高数据 |
| CS | PB0 | 低有效片选 |

USART1：PA9→USB-TTL RX，PA10←USB-TTL TX，GND 共地；115200、8数据位、无校验、1停止位、无流控，使用 3.3V 逻辑接口。板载 LED 使用 PC13，低电平点亮。

面包板中央两侧的五孔组互相独立；同一五孔组内部相通。OLED 七个引脚分别放入独立孔组，不能一起插进连通的电源轨。将开发板 3.3V/GND 引到红/蓝电源轨，再给 OLED 供电；较长面包板的电源轨可能分段，使用前检查通断。

软件 SPI 不使用 AFIO 重映射、不关闭 JTAG，不占 SPI1/SPI2 外设、DMA 或控制定时器。PB14 虽然有硬件 SPI2_MISO 复用功能，这里完全按普通 GPIO 使用。软件时钟使用标准库函数逐位翻转，频率受编译优化与任务抢占影响，不宣称固定频率；每次最多输出 8 字节且不关闭中断。

OLED 仍按 128×64、SSD1306 兼容、七针四线 SPI 模块初始化。LTP03A JY 丝印与照片不足以确认实际控制芯片，兼容性仍需上板验证。单向 SPI 没有应答，Ready=1 不能证明屏已连接。

## 三个应用任务

| 任务 | 优先级 | 初始栈 | 阻塞/唤醒方式 | 职责 |
|---|---:|---:|---|---|
| UART | 3 | 512字＝2048B | RX/TX 中断任务通知 | 接收、解析命令、独占 DMA 发送 |
| OLED | 2 | 384字＝1536B | 每1ms定期唤醒 | 分块刷新；每200ms更新界面 |
| LED | 1 | 128字＝512B | 等待队列或超时 | 接收新翻转间隔，超时翻转 PC13 |
| 内核空闲任务 | 0 | 128字＝512B | 无应用任务就绪时运行 | 空闲钩子 WFI，保持1ms系统时钟 |

数值越大，**任务优先级**越高；这与 NVIC 的中断优先级数值含义相反。表中栈是初始配置，需要在真实负载下通过 STATUS 查看余量再调整。

USART1 RX 使用 DMA1 通道5循环接收，HT/TC/IDLE 负责将数据搬入 FIFO 并通知 UART 任务；TX 使用通道4，完成/错误中断同样通知任务。中断里不解析命令、不打印、不刷新 OLED。通知可以合并，任务每次都读取 FIFO 和 TX 忙标志；一次 RX 通知不会被误当成 TX 完成。

LED 命令通过长度为1的队列 `xQueueOverwrite()` 交给 LED 任务，多条命令只保留最新间隔。收到新间隔后重新计时；持续快速修改间隔可能推迟下一次翻转。OLED 显存只有 OLED 任务操作；UART 和 OLED 的格式化输出共用互斥锁，释放锁后才等待串口 DMA。

UART 每轮最多处理64字节，达到预算后阻塞1ms，避免持续串口流占满 CPU。极端命令洪水下回复占用串口带宽，FIFO可能溢出；驱动记录 DROP，解析器丢弃受影响命令到下一个行尾后恢复，不承诺无限吞吐。

## 串口操作与显示

串口助手勾选发送换行，输入以下命令：

```text
HELP
STATUS
LED 100
LED 500
LED 2000
```

仅接受大写命令，CR、LF 或 CRLF 都可以结束一行；UART IDLE 仅通知收到数据，不代表完整命令。`LED n` 只接受 100～2000 的整数，单位是**相邻两次翻转间隔（ms）**：LED 500 对应亮500ms、灭500ms，完整周期约1秒。响应 `OK LED queued` 表示已入队，实际生效值随后由 LED 任务更新。空行忽略，超长、非法字符、越界数值返回 ERR，下一条完整合法命令可恢复。

OLED 显示示例（预期格式，并非实板截图）：

```text
FreeRTOS + SPL
UP:12s RX:30
LED:500ms ON
HEAP:xxxxB
```

第一行标明运行模式，第二行显示运行秒数及前台处理的接收字节数，第三行显示已生效间隔与 LED 状态，第四行是当前 FreeRTOS 堆余量。屏幕 RX 取模100000显示，STATUS 输出完整计数；长时间运行时一行16字符可能截断紧凑显示。

`STATUS` 还会输出最小堆余量 MIN、UART/OLED/LED 三个任务启动以来观测到的最小栈余量（字节）、DROP 和 ERR。这些值需要实板运行获得，不把初始栈大小当成实测栈余量。中断持续抢占、格式化输出等仍可能增加实际最坏栈需求。

## 移植关键点

- `Delay_Init()` 只检查时钟并配置 `NVIC_PriorityGroup_4`，不再初始化另一套 SysTick。官方 port.c 独占 SVC、PendSV、SysTick，通过 FreeRTOSConfig.h 中的宏绑定启动向量；User 里没有同名空函数。
- 系统节拍固定1000Hz；`Delay_GetTick()` 直接取内核 tick，`Delay_ms()` 使用任务阻塞延时。OLED 初始化、串口初始化均在调度器启动后的对应任务中完成。
- NVIC 全部分给抢占优先级；三个串口/DMA IRQ 均为6，允许调用 FromISR API，且彼此不嵌套。内核系统调用优先级阈值为5，SysTick/PendSV为15。硬件优先级0～4的中断不能调用 FreeRTOS API。
- 只使用 `heap_4.c`，预留10KiB；应用任务、空闲任务、队列和互斥锁都从中分配，不能在静态RAM占用上把这些任务栈再重复加一次。C运行库/启动文件的栈堆与RTOS堆是不同区域。
- 开启断言、分配失败钩子和栈溢出检测。异常后关中断、LED常亮，用调试器查看 `App_FaultFile / App_FaultLine`。这些是故障定位措施，不能替代实测栈余量。
- 尚未把 PID 电机控制并入本例程；本例程先演示任务、通知、队列和互斥锁。第五项闭环工程继续独立使用。

建议阅读顺序：User/main.c → System/App.c → User/FreeRTOSConfig.h → Hardware/Serial.c → Hardware/OLED_SPI.c。官方内核版本、许可证和哈希见 FreeRTOS/UPSTREAM.md。

## 验证与上板验收

已通过 Keil ARMCC5 全量编译、HEX/内存范围检查、SVC/PendSV/SysTick 和 UART/DMA 向量绑定检查，以及官方内核逐文件哈希复核。电脑端回归使用真实 DemoCommand.c 和 OLED_SPI.c，验证分段命令、边界/错误恢复，以及 GPIO 输出的 SPI 位序、CS/DC/RES 和长度边界；GPIO电平采用显式桩。这些测试**不执行 Cortex-M3 任务切换，也不验证电气时序**。

```powershell
# 在仓库根目录运行
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\build_all.ps1
python .\tools\check_projects.py
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\test_rtos_demo.ps1
```

上板按顺序检查：

1. 单独下载本工程，确认 PC13 默认约500ms翻转；串口出现 FreeRTOS + SPL 启动信息。
2. 接上本例程的 PB14/PB15 OLED 接线，观察界面更新，确认实际控制器兼容。
3. 发送 LED 100、LED 2000 和 STATUS，核对闪烁间隔、任务栈和堆余量；带换行测试非法命令后的恢复。
4. 同时接收串口、刷新屏幕并闪烁LED，长期观察 DROP/ERR、最小栈余量及故障变量；逻辑分析仪检查SPI时序。
